# Semantic markers, truthfulness and false positives

Read the relevant part of this page only after seeing a clue. Filtering only produces candidates; a verdict needs at least the actual location, context, applicable rule and impact.

## Content that only serves the session

| Clue | What to verify | Reasonable counterexample |
| --- | --- | --- |
| "I am role X", "the next agent continues", "ignore the previous text" | Whether collaboration workflow was put into business source files/user-facing docs, or is an approved product sample | Legitimate product test fixtures of a prompt editor |
| Session IDs, model or executor assignment, token accounting, task dispatch | Whether unrelated to running the business and only for this development handoff | Legitimate model fields in a cost-accounting product |
| "AI change this round", "adjusted per the user's last message" | Whether it replaces a business reason that should be explained, or depends on chat context that cannot be kept long-term | Copyright/provenance notices that must be kept |
| Dangling plan paths or temporary directories | Whether consumers can actually access them, whether temporary evidence is mistaken for a permanent runtime dependency | Project-approved collaboration-record entry and real index |

"Generated by tool X", if it is a generator's fixed format or a license/provenance obligation, is traced to the generation source and contract first; never delete it from the output by hand. Legitimate AI terminology, agent modules, variable names and Chinese punctuation carry no independent violation meaning. Ordinary business TODOs may stay; whether they should be done depends on current acceptance, not on the word TODO appearing.

## Does the comment tell the truth

First split the assertion into observable propositions, then read the related implementation: defaults -> actual initialisation and override layers; retry -> outer callers and termination conditions; permissions -> the real authoritative exit; caching -> write/invalidation paths; thread safety -> shared state and synchronisation boundaries. Reading only a few lines near the comment is usually not enough to refute global behaviour.

For example, "automatically retries three times on failure" with only one call: first check whether the caller/library retries, then decide between false statement and insufficient evidence. The correct fix may be changing the comment or may require implementing per the original approval; this package only reports the factual difference and does not choose product behaviour itself.

Incident notes, data compatibility background, algorithm derivations and necessary limitations are facts for later maintenance; they are not deleted for being long or dated. An outdated description needs current version/implementation evidence; author tone or formatting style does not prove it outdated.

## Empty shells, templates and ineffective verification

- Empty functions or fixed return values: verify whether publicly reachable, whether an approved interface stub/test double, whether acceptance requires a real implementation. The impact of a missing implementation must land on concrete user behaviour.
- Duplicated checklists: verify whether they store the same fact again when an authoritative source exists, or whether different objects need independent evidence. Do not treat every template row as unfinished body text.
- Tests without explicit assert: some tests rely on snapshots, type checks, framework exceptions or external assertions; verify the runner and expectations first. Report ineffective coverage only when the test cannot fail on a target error; never rely only on text search for assertion keywords.
- Unjustified defensive code: verify whether input can be empty, who owns the boundary, whether degradation is approved. Returning empty may satisfy the fault-tolerance contract or may swallow a critical error; distinguish by the actual contract, never delete wholesale.

Defects in generated artefacts point to the generation source and rebuild steps; the review only describes verification suggestions and does not run the generator or modify third-party files. When performance, style or file size have no substantive impact, list them as optional; never use a collaboration-trace audit to force a large refactor.

## Reporting and fix boundary

A confirmed issue records the triggering rule, the text's purpose or provable factual difference, concrete impact and a minimal candidate fix; reasonable exceptions also record the reason, to prevent mechanical deletion next time. Unverified clues state which call chain, configuration or source is missing. Results contain no authorship probability and never treat use of AI tools as an issue in itself.

File hashes stay unchanged during a read-only review. Historical material that must be kept is first handed to the project's existing archive or collaboration-record contract; do not pile all audit findings into the code long-term; archiving is not this package's default action. After a fix, verify only the actual impact and adjacent false positives; do not expand deletion in pursuit of zero keywords.
