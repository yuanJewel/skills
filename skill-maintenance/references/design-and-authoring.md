# Design and authoring method

For new packages, method revisions and extraction from old material. A small erratum verifies only the relevant sources, impact and examples; it does not restart the full process.

## Decide from the requirement whether a package is warranted

First express the requirement as one observable behaviour, e.g. "review a schema change and give a compatibility verdict for old readers/new writers and mixed deployment", not "provide professional advice". Check existing packages' description, routing and topics: the same input/artefact/decision belongs to one authority; if only project parameters differ, feed them into the existing method. Split a package only when the capability can be triggered independently, has its own failure recovery and is often used on its own. When the output purpose is the same but the trigger phase differs, there may be entry routing, without copying the method.

Walk one real or explicitly synthetic request through to the artefact and list the decisions a model easily gets wrong on common sense alone. For each decision state: what evidence is needed, how branches are distinguished, the next action, what is kept on failure, and what evidence ends it. If deleting a passage changes no judgment, it usually does not deserve to stay in the body. If there are only headings and slogans like "ensure correctness", the method is not finished yet.

## Extract from the two kinds of source separately

Mature external methods provide transferable steps and style; old workspace material provides real constraints, mistakes and retention obligations. Register the two independently; two copies of the same upstream do not count as dual sources. For each point actually adopted record pinned version/section, adopted method, dropped bindings, own-authored additions, landing location and conflicts. Parts without sufficient sources are marked "own-authored, pending behaviour verification"; never fabricate historical support to make up dual sources.

Classify old material item by item into: general decision method, current project fact, historical evidence, deprecated rule, conflict pending verification. Methods may enter the package; addresses, role names, models, quotas, sessions and logs go to project inputs or the task archive. Commands, read-everything requirements and permissions from old material must not be transplanted directly. For a conflict, first compare the current user instruction, approved requirements and version evidence; when still undecidable, keep both interpretations and the dependent actions, and do not pick whichever is most convenient.

Example: the old rule "read all material every time" keeps the purpose "restore valid constraints at start", changed to entry -> relevant index -> sources needed for the decision, and verified so that a missed read reveals the gap. The old rule "write all files once design approval arrives" must not be carried over; write scope is decided by the current implementation request. An old "success log" is only a lead for failure cases and does not support that a new host has passed.

## Write one complete path first, then split files

1. Write the normal artefact from a concrete input. Add adjacent wrong requests, e.g. a request only to review should not automatically fix files; a request only to use a skill to produce a report should not maintain the skill.
2. Write the description: capability, applicable conditions, easily confused exclusions. When trigger tests fail, first check whether boundary and artefact are clear, then change wording; do not pile on industry keywords or "must always use". Balance length against the target host's measured budget; do not truncate at a generic 120 characters.
3. Write `SKILL.md`: required inputs, key branches, completion conditions and when to read supporting pages. Supporting pages carry complex conditions, composition details and recoverable flows; connect them with real Markdown links. Never write "see the docs" without a location, nor require reading all supporting pages every time.
4. Templates are only for actual artefacts and state who fills them, required evidence and how to write missing items. Use explicit variables such as `{{field}}`; never pass off unfinished author prose as a template. Scripts are only for repeated deterministic processing; first define input, output, errors, read-only/write scope and recovery, then implement. Tests, benchmarks and session output go to the task verification directory.
5. Check depth with a concrete artefact: can the consumer complete the decision from the inputs, do they know where to stop after failure, is the evidence enough for another person to review. Add missing decisions, not extra tutorials.

Identical form does not mean they should merge: deployment recovery and material archiving both write "rollback", but the recovery object and correctness differ; do not keep only one abstract rollback passage. Conversely, several packages each copying the user workbench template creates multiple authorities; reference the existing single contract.

## Implementation control and feedback revision

Before writing, verify the task's allowed directories, candidate version and who is currently writing. A package author writes only their own package; the library ledger and public index go to the sole integrator. After the candidate changes, re-identify it; never sign new bytes with an old report. When licensing cannot be satisfied, a shared interface changes or behaviour exceeds scope, hand over the gap and the partial candidate clearly; do not expand into other packages to hide the problem.

Read evaluation traces, not only the final answer: is the error from not triggering, reading the wrong supporting page, missing input, insufficient method, unavailable environment or a biased judge. Fix the minimal cause and rerun affected cases and adjacent negative cases; test generalisation with held-out cases not involved in the rewrite. One example should not be promoted into a mandatory step for all tasks. When successive revisions bring no improvement, stop expanding and return to capability/boundary design.

Design completion hands over the design card and unverified points; implementation completion hands over version, candidate digest, file classification, verification and upgrade impact. Do not call author self-check independent acceptance, and do not accumulate an unbounded changelog inside each package.

## Library-wide author conventions

These conventions apply to all packages in the library and are enforced on new writing or modification; for existing packages, fix whatever part you touch per the conventions; do not rewrite the whole library just to unify format.

1. **Sources section**: under `## Sources`, exactly three numbered items. (1) Source ID and link to the pinned-version original; (2) what was adapted, own-authored and dropped; (3) location of the license file shipped with the package and the library-root third-party notice (in this library `THIRD_PARTY_NOTICES.md`). Do not link internal source ledgers that are not published with the library.
2. **License files**: at the package root, named `LICENSE-<source abbreviation>.txt` (e.g. `LICENSE-EC.txt`), byte-identical to the upstream license at the pinned version; the same source has the same hash in every package. Apache-2.0 sources must ship a package-root `NOTICE.md` stating adapted files and a modification record (append one line per change); for MIT sources the adaptation note is carried by item (2) of the Sources section. No `licenses/` subdirectory, no other naming.
3. **Placeholders**: fields to fill in `assets/` templates and supporting-page examples are uniformly written `{{field}}`; tool-native syntax (JJB `{name}`, API path parameters, shell `${VAR}`) stays as-is. No TODO/TBD left in the body.
4. **Script exit codes**: only 0 = pass, 1 = noncompliance found, 2 = input or runtime-condition error. Subdivisions such as "candidate changed" or "read unstable" go into JSON `status` and take no new exit code. Error messages give a constant, specific reason, never raw platform errno text, path bytes or file content; symlink, out-of-root and missing items each have their own code.
5. **Readability**: one judgment per sentence. Write inputs as lists; missing branches as "missing X -> do Y"; steps as "what to do / stop condition / artefact". Keep single source lines under about 200 characters; beyond that split into lists or sentences.
6. **Referencing other packages**: when consuming another package's contract, template or definition, write the package name, e.g. "status meanings per `verification-gate`". Each definition is maintained in only one package.
7. **Terminology**: no internal governance-plan terms (such as channel, model pool, usage quota). Resource recommendations use grade words (e.g. `low/low`, `normal/medium`, `normal/high`; first the cost tier, then the reasoning tier) and declare that grade words map to actual execution configuration through the project resource mapping; executor count, concurrency quotas, machines and environments are host limits supplied by project configuration. Wording such as author self-check, receipts and the extraction process does not enter consumer-facing text.
8. **Project entities**: a specific project's rules, roles, permission categories, domains, directories and platform combinations appear only as "project input", "[example; replace per project contract]" or a conditional ("if the project contract lists ... as ..."), never as general rules.
9. **Official links**: when carrying a fragment anchor, verify the page's actual id; if it cannot be verified, link only the page.
10. **Resource cleanup**: packages whose method creates containers, images, processes, temporary files or test data on the local machine must state wrap-up cleanup steps and reference the local resource cleanup rules of `task-implementation` by package name; the package adds only its domain-specific objects and writes no separate rule set. Clean up only own objects registered this run; write no global cleanup command.
11. **Language**: all published repository content (SKILL.md, references, assets, scripts, NOTICE files, changelog) is English only. The root README has an English default `README.md` and a Chinese twin `README.zh.md`; only this twin may carry non-English prose.
