# Compatibility, shared upgrades and the checker

## Host facts and compatibility requirements

First list the required hosts/versions and discovery mechanism, then verify supported fields, invocation/reasoning controls and path boundaries against current official documentation. Record three columns separately: documented support, allowed by current configuration, observed to take effect; do not treat one host's metadata, directories, CLI or environment variables as a contract for all hosts.

Minimal real verification starts from one isolated package: link the target discovery directory to the real package, read the display related to localised (e.g. Chinese) name/description and the body, actually reference one supporting page and observe its content being used; launch once from the project root and once from each subdirectory that must be supported. The standard `name` stays the package identifier; localised display names or user role entries are verified per the host mechanism, and a role name never becomes a permission. Cleanup targets only this test's copy/discovery entry and keeps result evidence; never mix a temporary hello package into the formal inventory.

When the host offers no model/reasoning-tier setting or the field is unsupported, record "not settable/unverified"; do not pass off a prompt as a parameter, and do not privately install tools or switch service provider to complete the test. Keep optional fields; warn on unknown fields and re-verify per host; do not delete them all just because lint does not recognise them.

## Lint inputs and outputs

The formal program is read-only. Python restricted YAML supports two-space mappings and single-line plain/single-quoted/JSON double-quoted scalars; sequences, block scalars, anchors, tags and other YAML features exit `2`, meaning insufficient capability or not reliably decidable; this cannot be used to call valid YAML illegal. Duplicate keys, missing required fields, name/real-directory mismatch and field length beyond the specification are `1`. The single-field 1024-Unicode-character check on description and the host discovery listing budget are two separate things; there is no 120-character hard gate.

Type checks cover only name/description and fields this program consumes from explicit configuration; full types/semantics of optional standard fields such as metadata and license, and of host extensions, are not validated and must be verified separately against the target standard and host. An explicit null cannot then take a child mapping; reserved indicators, non-YAML-printable characters and other unparseable input return 2. Explicit JSON rejects NaN/Infinity and numbers that overflow to non-finite values, rather than swallowing them as legal unknown fields.

- Positional argument: a single package directory, which may be a discovery symlink. The real package root is the default readable root; when the package links to library-root files, declare the library root with `--allow-reference-root`, otherwise those links report `outside_allowed_root`.
- `--allow-reference-root DIR`: extra root that references may reach, repeatable; not an authorisation to scan the whole directory. Markdown inside the package is fully checked; in external roots only actually referenced Markdown is read. Scripts, images and the like are checked only for existence and path, never executed or read.
- `--node FILE --marked-module FILE`: both explicitly specify an already installed, trusted parser. They are first resolved to existing absolute real paths, and the location check and execution use the same result, with no re-lookup via PATH. The program strips `NODE_OPTIONS`/`NODE_PATH`, does not search host-private paths automatically and does not install. Neither may be inside the checked package; the module itself is executable code, so the caller must choose a trusted source.
- `--host-config FILE`: explicit JSON; may contain `host`, `version`, a `supported_fields` string array and the `description_budget` below. Existing fields not in supported_fields go only into host-pending warnings, not standard errors.
- `--description-set FILE`: explicit JSON `{"entries":[{"name":"package-a","description":"description"}]}`; only this set is summed, names are deduplicated, invalid data exits `2`. It does not scan all install directories and does not assume the set is complete.

The `description_budget` format in the host config is `{"scope":"descriptions-only","limit_characters":8000,"evidence":"location of user measurement record","measured_at":"measurement date"}`. The numbers are only an example, not a built-in default. A comparison requires both an explicit set and the user's measurement evidence; otherwise a capability/input gap is returned. The report states actual character count, denominator/scope and an over-limit recommendation; exceeding is not a Skill format error. This metric only sums Unicode characters of descriptions; it does not estimate tokens and excludes path/listing wrappers; the host's actual total context must be measured separately. Recording user-supplied evidence does not mean the program independently verified it.

The placeholder check targets explicit author scaffolding markers in frontmatter and in the rendered text of non-template Markdown, such as `[TODO: write steps]`, `<TBD>`, and `TODO:`/`FIXME:` at line start. It ignores code examples; in-package `assets/` are consumer templates and may hold `{{field}}`/example placeholders; external references get no exemption just because a directory happens to be named assets. Whether a template is filled in is checked by the task that uses it. Merely mentioning the TODO concept, ordinary "pending verification" wording or legal variables is not flagged as unfinished. The checker does not understand semantics and cannot find all unfinished writing.

Markdown is parsed with marked tokens, covering inline/reference links, images, encoded paths and nested brackets; HTML-native links, remote reachability and fragment anchors are not checked. Paths are first normalised to real addresses before the allowed-root check; file descriptors are opened component by component without following symlinks, and directories/reads are re-checked before, after and at the end; any observed change gives `2`. Circular Markdown references are deduplicated and terminate; directory symlink cycles report an error. The program does not lock writers, provides no transactional snapshot and cannot prove files stay unchanged after it returns; formal review still pins the candidate and re-verifies before key actions.

The JSON contains `schema_version` (currently 2; argument errors output the same version), `status`, `errors`, `input_errors`, `warnings`, `host_pending`, local counts, the description summary and capability limitations. Exit codes: `0` (`passed`) = supported scope checked; `1` (`noncompliant`) = specification/boundary problems found; `2` (`incomplete`) = input, parsing capability or read stability insufficient, check incomplete. When errors co-occur, `2` takes precedence and the report keeps all findings; upstream must not look only at the exit code and drop the unverified scope. On config, parser, timeout or permission failure, findings so far are kept; nothing is installed automatically and read roots are not widened.

## Upgrade and recovery

1. Pin the shared original, discovery entry, version digest, allowed change scope, sole writer and consumer list. Confirm whether it is a true shared reference or a copy; a copy must record its version independently and cannot claim to be upgraded together.
2. Classify the change: pure wording fix, compatible addition, trigger/input/output semantic change, dependency/license change. Use the library's existing versioning policy; where input or trigger semantics are incompatible, state the migration explicitly; a version number does not replace impact analysis.
3. Complete static, script and affected-behaviour checks in the candidate directory. Bind the review report to the new digest and verify each consumer's policy/parameters and necessary hosts; consumers without permission or unavailable stay pending; one project passing is not generalised to all.
4. Perform release actions within the task's authorised scope. Never silently change entries, roles or configuration of all consuming projects. Library-level version/source/impact records are updated by the sole maintainer; the package holds only the current version and necessary notices.
5. Consuming projects confirm the version read at a new phase or key step. When an already-loaded session cannot confirm a refresh, explicitly re-read or verify in a new session on the applicable host; do not poll the platform in real time.
6. After verification clean up your own temporary inputs, parser caches and discovery test links; archive non-reproducible evidence, approval originals, old candidates and recovery pointers per the retention method. Check references before deleting; "an old copy exists" is not a verified recovery.

On an upgrade anomaly, first stop affected subsequent writes and record consumers, current version and in-flight work; restore the matching package/dependencies/entries to the approved recovery point, then re-verify licensing, references and minimal behaviour. When the old version does not meet current policy or is known harmful, do not roll back blindly; keep it isolated and hand over concrete options. Recovery may change only the authorised object; never clear the whole library or remove others' candidates.
